Da planilha bagunçada ao modelo relacional: 1FN, 2FN, 3FN e BCNF na prática

Um telefone, doze linhas

Imagine que uma cliente da nossa loja de papelaria mudou de telefone. Na planilha de pedidos, o número dela aparece em doze linhas. Corrigimos onze e esquecemos uma. Agora a mesma cliente tem dois telefones, e ninguém sabe qual é o certo.

Esse tipo de problema tem nome: redundância, que é o mesmo dado guardado em vários lugares. Neste artigo vamos mostrar como as formas normais (1FN, 2FN, 3FN e BCNF) organizam uma tabela para que cada fato fique guardado uma única vez. Você vai aprender a enxergar o problema numa tabela, corrigi-la com SQL e saber quando parar.

Usamos PostgreSQL 16 com o pgAdmin 4 e apenas dados fictícios. Todos os scripts estão na pasta sql/ do repositório.

A planilha com problema

Esta é a nossa tabela única, pedidos_planilha. Cada linha é um produto de um pedido.

Dessa repetição nascem três anomalias:

  • Atualização: mudar o telefone da Ana exige alterar todas as linhas dela. Esquecer uma deixa o dado inconsistente.
  • Inserção: não dá para cadastrar um produto novo enquanto ninguém o comprou, porque toda linha precisa de um pedido.
  • Exclusão: se apagarmos o único pedido que tem a caneta, o preço da caneta some junto.
-- sql/01_planilha_inicial.sql | PostgreSQL 16 | dados fictícios
UPDATE pedidos_planilha SET telefone = '11 98888-0001'
WHERE id_pedido = 1 AND produto = 'Caderno';  -- e a linha da Caneta?

1FN, 2FN e 3FN passo a passo

1FN: uma informação por célula

Na prática, a planilha às vezes traz vários produtos na mesma célula, como "Caderno, Caneta". Assim não conseguimos somar quantidades nem filtrar por produto. A 1FN pede valores atômicos, ou seja, indivisíveis: cada produto do pedido vai para a sua própria linha. A tabela da Figura 1 já está assim, e por isso já está na 1FN.

Antes de seguir, precisamos de dois termos. A chave primária é a coluna (ou o conjunto de colunas) que identifica uma linha sem repetição. Aqui ela é o par (id_pedido, produto). Uma dependência funcional A → B significa que, sabendo o valor de A, sabemos o único valor possível de B. Por exemplo, produto → preco_unit.

2FN: nada pode depender de só uma parte da chave

O preço depende apenas do produto, e o telefone depende apenas do pedido. Nenhum dos dois depende do par inteiro. Isso é uma dependência parcial, e é ela que causa a repetição da Figura 1. A 2FN manda separar:

  • produtos (id_produto, nome, preco_unit)
  • pedidos (id_pedido, cliente, telefone, cep, cidade)
  • itens_pedido (id_pedido, id_produto, quantidade)

3FN: nada pode depender de quem não é chave

Em pedidos, a cidade depende do CEP, e o telefone depende do cliente, não do pedido. Temos dependências transitivas: id_pedido → cep → cidade. A 3FN separa cada uma em sua tabela.

-- sql/04_3fn.sql | PostgreSQL 16
CREATE TABLE ceps     (cep VARCHAR(9) PRIMARY KEY, cidade VARCHAR(60) NOT NULL);
CREATE TABLE clientes (id_cliente SERIAL PRIMARY KEY, nome VARCHAR(100),
                       telefone VARCHAR(20), cep VARCHAR(9) REFERENCES ceps);
CREATE TABLE produtos (id_produto SERIAL PRIMARY KEY, nome VARCHAR(100),
                       preco_unit NUMERIC(10,2));
CREATE TABLE pedidos  (id_pedido SERIAL PRIMARY KEY,
                       id_cliente INT REFERENCES clientes);
CREATE TABLE itens_pedido (
  id_pedido  INT REFERENCES pedidos,
  id_produto INT REFERENCES produtos,
  quantidade INT NOT NULL,
  PRIMARY KEY (id_pedido, id_produto));

Cada REFERENCES é uma chave estrangeira: uma coluna que aponta para a chave primária de outra tabela. Ver o script completo

Agora o telefone da Ana é alterado em uma linha de clientes. Um produto novo entra em produtos sem precisar de pedido. Apagar um pedido não apaga o preço. As três anomalias sumiram.

Quando a 3FN não basta: BCNF

Veja uma tabela de matrículas. Cada professor leciona uma única disciplina, e um aluno tem um único professor em cada disciplina.

Essa tabela já está na 3FN, mas ainda repete dados. Se o Prof. Lima passar a lecionar outra disciplina, teremos de alterar várias linhas. O motivo é professor → disciplina: o professor determina a disciplina, mas professor não é chave da tabela. A BCNF (forma normal de Boyce-Codd) exige que todo determinante seja chave. A correção:

-- sql/05_bcnf_horarios.sql | PostgreSQL 16
CREATE TABLE professores (professor VARCHAR(60) PRIMARY KEY, disciplina VARCHAR(60));
CREATE TABLE matriculas  (aluno VARCHAR(60),
  professor VARCHAR(60) REFERENCES professores, PRIMARY KEY (aluno, professor));

Ver o script completo

Custo escondido. A regra "cada aluno tem um professor por disciplina" não é mais garantida pela estrutura. Em tabelas separadas, o banco deixaria um aluno ter dois professores da mesma disciplina. Esse é o limite da BCNF: ela às vezes não preserva todas as dependências, e então precisamos de uma regra extra (um gatilho, por exemplo).
Aprofundamento: definições formais

Dada uma tabela R e conjuntos de colunas X e Y, dizemos que X → Y quando duas linhas com o mesmo X têm sempre o mesmo Y. Uma chave candidata é um conjunto mínimo de colunas que determina todas as outras. R está na 3FN se, para cada dependência não trivial X → A, X é uma superchave ou A faz parte de alguma chave candidata. R está na BCNF se, para cada dependência não trivial X → A, X é uma superchave. Na tabela de matrículas, as chaves candidatas são (aluno, disciplina) e (aluno, professor). Por isso disciplina faz parte de uma chave, a 3FN aceita professor → disciplina, e a BCNF não.

Erros comuns e limitações

  • Normalizar sem olhar os dados. Dependência funcional é uma regra do negócio, não do formato da tabela. Confirme com quem conhece a loja se "cada CEP tem uma cidade" é mesmo verdade.
  • "Sempre normalize até a 3FN". Em relatórios e análises, tabelas achatadas costumam ser mais rápidas porque evitam junções. O custo é cuidar da consistência. Este assunto é a desnormalização, que merece um artigo próprio.
  • Esquecer as chaves estrangeiras. Separar tabelas sem declarar REFERENCES traz de volta o problema que queríamos resolver.
  • Limite deste texto. Não cobrimos a 4FN e a 5FN. Elas tratam de redundâncias que surgem quando uma tabela mistura fatos independentes.

Como começar na área

Pegue uma planilha sua (de gastos, de estudos, de um time) e tente achar as dependências funcionais. Depois crie as tabelas no PostgreSQL, insira dados fictícios e tente provocar as três anomalias antes e depois da separação. Praticar com um exemplo que você conhece ensina mais do que decorar definições.
